# Техническое задание: ansible-awg-gateway

## 1. Назначение проекта

Разработать open-source Ansible-проект для автоматизированного развёртывания и управления частной VPN-инфраструктурой на базе AmneziaWG 3.1.

Репозиторий: `ansible-awg-gateway`\
Платформа: GitLab\
Лицензия: Apache License 2.0

Проект предназначен для личной инфраструктуры, homelab и защищённого удалённого доступа.

Основные принципы:
- Минимальная сложность.
- Идемпотентность Ansible.
- Использование стандартных модулей `ansible.builtin`, где это возможно.
- Отсутствие Docker, Kubernetes и веб-панелей.
- Отсутствие избыточных абстракций и дополнительных Python-утилит без необходимости.
- Безопасная работа с приватными ключами.

## 2. Архитектура

```text
iPhone / Windows / Linux
          |
          | AWG 3.1
          v
     VPS Россия
     awg-client
     awg-backbone
          ^
          | AWG 3.1 / UDP
          | Инициатор: VPS NL
          |
    VPS Европа
          |
          v
       Интернет
```

Используются два независимых AWG-туннеля.

### Российский VPS

- Принимает подключения клиентских устройств с динамическими IP.
- Принимает межсерверное AWG-соединение от нидерландского VPS.
- Маршрутизирует клиентский трафик через зарубежный узел.
- Использует `nftables`.
- Не предоставляет публичной панели администрирования.
- Сохраняет SSH-доступ при изменениях маршрутизации.

### Нидерландский VPS

- Инициирует межсерверное UDP-соединение с российским VPS.
- Выполняет роль выходного шлюза.
- Обеспечивает NAT для клиентского трафика.
- Не публикует отдельный VPN-порт для межсерверного подключения.
- Использует `nftables` с минимально необходимыми разрешениями.

Важно: AWG использует UDP, поэтому поведение инициирования соединения нужно проверить экспериментально. Не считать его эквивалентом направленного TCP-соединения.

## 3. Безопасность

Обязательные требования:

- `nftables` с политикой `default drop`.
- Доступ к межсерверному AWG-порту российского узла только с разрешённого зарубежного IP.
- Аутентификация клиентских устройств по индивидуальным ключам.
- Отсутствие публично доступных административных сервисов.
- Защита приватных ключей.
- `no_log: true` для задач обработки секретов.
- Безопасное применение firewall с защитой от потери SSH-доступа.
- Запрет утечки клиентского трафика через российский внешний интерфейс при отказе межсерверного туннеля.
- Отдельная обработка IPv4 и IPv6: не объявлять IPv6-маршруты клиентам, пока они не настроены полностью.

Не использовать TCP tarpit, honeypot или искусственные задержки в первой версии.

## 4. Ansible

Предварительная структура:

Структуру можно уточнить, если будут объективные причины. Не создавать отдельную роль для каждой небольшой операции.

Требования:

- Повторный запуск не должен пересоздавать ключи.
- Изменение клиентов не должно прерывать существующие подключения.
- Все конфигурации формируются через Jinja2.
- Секретные файлы не попадают в Git.
- Реальные inventory и клиентские конфигурации хранятся локально.
- Версии пакетов и источники установки явно документируются.
- Изменения конфигурации проверяются до применения.

## 5. Управление клиентами

Реализовать отдельный playbook `clients.yml`.

Предполагаемые операции:

```bash
ansible-playbook playbooks/clients.yml \
  --tags client_add \
  -e client_name=iphone

ansible-playbook playbooks/clients.yml \
  --tags client_remove \
  -e client_name=iphone

ansible-playbook playbooks/clients.yml \
  --tags client_list
```

При создании клиента:

1. Проверяется уникальность имени.
2. Выделяется свободный IP-адрес.
3. Генерируется индивидуальная пара ключей.
4. Peer добавляется на российский сервер.
5. Конфигурация сохраняется на управляющей машине.
6. Создаётся профиль для AmneziaWG 3.1.
7. Генерируется совместимая ссылка `vpn://...` для AmneziaVPN.
8. Генерируется QR-код подключения.
9. Выводится краткий результат выполнения.

Пример локального результата:

```text
clients/
└── iphone/
    ├── iphone.conf
    ├── iphone.png
    └── iphone.url
```

Требования:

- Конфигурации создаются локально через `delegate_to: localhost`.
- Приватные файлы имеют права `0600`.
- QR-коды не попадают в Git.
- Поддерживается повторная выдача существующей конфигурации.
- Удаление клиента не затрагивает остальных.
- Сохраняется постоянное состояние зарегистрированных клиентов.
- Не допускается повторное выделение уже занятого адреса.

Критично: формат `vpn://` нельзя придумывать самостоятельно. Необходимо изучить актуальную реализацию импорта AmneziaVPN и подтвердить поддержку AWG 3.1. До проверки не считать функцию завершённой.

## 6. Проверка работоспособности

Создать `validate.yml`.

Проверять:

- Состояние AWG-интерфейсов.
- Наличие и актуальность handshake.
- IP forwarding.
- Корректность маршрутов.
- Работу NAT.
- Доступность внешней сети через зарубежный VPS.
- Отсутствие утечек через российский шлюз.
- Восстановление после перезагрузки.
- Поведение при недоступности межсерверного туннеля.

Предусмотреть диагностику прямого и обратного UDP-обмена с использованием `tcpdump`, не сохраняя содержимое пользовательского трафика.

Не считать наличие handshake доказательством корректной маршрутизации.

## 8. Порядок разработки

Работать по этапам:

1. Изучить актуальные AmneziaWG 3.1, форматы конфигураций, поддержку Linux и AmneziaVPN.
2. Составить архитектурный план с учётом особенностей UDP.
3. Реализовать установку и настройку межсерверного AWG.
4. Реализовать firewall, маршрутизацию и NAT.
5. Реализовать клиентский AWG.
6. Реализовать выпуск, отзыв и экспорт клиентских подключений.
7. Проверить генерацию QR и `vpn://`.
8. Добавить автоматизированные проверки.
9. Подготовить публичную документацию.
